# Browser distribution

The NSIS installer registers the same bounded Native Messaging host for Chrome, Edge, Brave, Chromium and Firefox under the current user's account. Repeated installation and runtime repair replace only Flux's manifest values; uninstallation removes registrations owned by the installed executable. Browser cookies and download history remain in the browser profile.

Chromium host manifests contain `allowed_origins`; Firefox uses `allowed_extensions` and the stable `flux@flux-download.local` identity. The host independently checks launcher arguments before reading its four-byte framed input. Chromium store IDs can differ: put the approved IDs in `native-host/chromium-extension-ids.json` before building the desktop release. The shared unpacked extension ID remains included. Do not put OAuth credentials or Mozilla signing tokens in this file.

Run `./scripts/package-browser-stores.ps1` to create runtime-only Chrome, Edge and Firefox store ZIPs, then `./scripts/verify-browser-stores.ps1` to verify their exact file set and source hashes. Chrome and Brave use the Chrome Web Store distribution; Edge can use its own reviewed store listing or the Chrome Web Store version. The `Prepare browser store packages` workflow validates the production Gecko manifest and prepares the same ZIPs. It can request an unlisted Mozilla signed XPI when explicitly enabled with repository secrets `AMO_JWT_ISSUER` and `AMO_JWT_SECRET`.

Upload `Flux-<version>-chrome-store.zip` to the Chrome Web Store. The store packager removes the development `key` and any self-hosted `update_url` from Chromium store manifests. GitHub/unpacked packages keep their stable development key. The verifier permits only these manifest differences and checks all other runtime files against the shared sources. The store assigns its own item ID: record that ID in the desktop native-host allowlist before distributing the store extension to users. Uploading an ordinary `Flux-<version>-chrome.zip` is not the store packaging path.

Normal Windows Chrome installations require a Web Store listing for consumer installation without developer mode. Standard Firefox requires Mozilla signing for permanent installation. Store publication and signing depend on the account's permissions and review; the application does not bypass these checks or force browser enterprise policies. Native host registration is automatic once the application is installed. The prepared local ZIPs have no store signature.

The Firefox 140+ package declares authentication, browsing and website content transfer for its local desktop integration. Firefox 120–139 uses explicit native-transfer consent in its settings and a DOM/network fallback where MAIN-world script injection is unavailable. The modern manifest declares Firefox for Android 142 as its minimum schema version; distributed desktop hosts target Windows x64 and Linux x86_64. Browser installation tests run on Windows. The Linux package checks per-user host manifests and authenticated Native Messaging separately; Flatpak/Snap browser confinement is outside that test scope.

## Chrome Web Store draft identity

The Chrome Web Store listing uses `okimieponfbegjhmfdnnefnddofooipk`. This exact identity is included in the desktop allowlist alongside the existing unpacked identity. Previously published 2.4.2 desktop packages predate this store identity and do not acquire the updated allowlist from an extension upload. Flux 2.4.3 desktop packages include both identities; Windows installer tests and installed Linux RPM tests cover both origins. The store listing remains subject to Google review. Do not work around the missing identity with wildcard origins or browser enterprise policies.

## Privacy disclosure for store listings

Since 2.4.2, the extension checks GitHub release metadata when its popup opens, with a six-hour cache and offline retry backoff. The request contains no page URLs, download history, cookies or authorization headers from the browser. GitHub receives ordinary connection metadata (including the IP address) required to serve that request. Live connection tracking sends only the extension version to Flux on this computer; the authenticated native socket defines its lifetime. These messages do not install extensions or change browser permissions. The popup explains that the free Flux desktop app is required and links to the official release downloads.

Flux detects media requests and media elements on HTTP(S) pages. Native transfer is initiated by a user action or an enabled download interception preference. The extension shares selected source URLs, titles, format metadata, bounded HLS/DASH manifest snapshots and origin-scoped session credentials with the local Flux application. Firefox local transfer requires consent. Request headers are kept in session storage, durable transfers use protected credentials, and public task responses omit authentication secrets. There is no analytics endpoint or remote Flux account. Downloading media contacts the selected source's servers and, for torrents, the swarm, trackers and DHT. Torrent sharing follows the configured global or per-task rule; the default ratio is 1.0. Users can disable sharing or pause it explicitly. Enabled Debrid accounts contact the selected service API using the stored encrypted key. Desktop update checks contact GitHub Releases at startup or on demand.

Sources: [Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [Edge Native Messaging](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/native-messaging), [Mozilla signing and distribution](https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/).

GitHub serves release metadata and packages according to its [privacy statement](https://docs.github.com/en/site-policy/privacy-policies/github-general-privacy-statement). Optional Debrid services and download providers receive the requests needed for the user's selected transfer; their privacy policies apply to those requests. The prepared [code signing policy](code-signing-policy.md) uses SignPath for maintainer release infrastructure after approval. Signing does not send users' downloaded files, browser cookies or session credentials to SignPath; maintainers' use of that service is covered by [SignPath's privacy policy](https://signpath.io/privacy-policy).

## Flux 2.6.0 distribution identities

The Firefox store ID is `firefox@fluxdownload.org`, while GitHub packages retain `flux@flux-download.local`. Desktop 2.6.0 authorizes both explicitly in host registration and caller validation. Chrome store identity remains `okimieponfbegjhmfdnnefnddofooipk`. Store submission ZIPs are publisher build artifacts and are not public GitHub release assets. Neither store approval nor browser update delivery is immediate.
